# AI 请求状态与课程阶段恢复设计

## 目的

解决课程正文校对、翻译无法完整完成的问题，并让“仅补充校对”和“仅补充翻译”
在用户确认后一定真正重新调用对应 AI 服务。

本文件是下一轮实现的设计约束。实现前先阅读本文件、
`docs/feedback/2026-09-20-ai-round-diagnostics.md` 和项目 `AGENTS.md`。

## 已确认问题

最近课程记录显示：AI 请求已经发出，但客户端没有收到完整响应，当前请求被标记为
`uncertain`。为避免重复处理，旧逻辑会阻止后续请求；用户选择补做阶段时，
如果没有把对应请求 ID 放入授权列表，补做任务仍然不会调用 AI。

当前代码还把以下概念分散在 `src/dispatch.rs`、`src/llm.rs`、`src/pipeline.rs`、
`desktop/src/workspace.rs` 和 `desktop/src/task_ui.rs`：

- 单个逻辑段是否完成
- 某一次网络请求是否已经发送
- 服务是否明确拒绝
- 客户端是否收到完整响应
- 用户要补做哪个阶段
- 哪些未知请求允许重新发送

后续实现必须把这些概念分开，避免继续在 `resend: Vec<String>` 和全局阻止逻辑上叠加特例。

## 目标状态模型

每个 AI 逻辑处理单元拥有稳定 ID：

```text
logical_id = task_id + stage + segment_id
stage = proofreading | translation | summary
```

逻辑单元不是一次网络请求。一个逻辑单元可以有多次请求尝试。

### 请求结果

每次尝试只能归入以下状态：

| 状态 | 含义 | 是否可自动重试 | 是否需要人工授权 |
| --- | --- | --- | --- |
| `completed` | HTTP 成功且响应通过结构校验 | 否 | 否 |
| `failed` | 明确知道请求未产生可用结果，例如 400、无效 JSON、段落不匹配 | 按策略可重试 | 否 |
| `uncertain` | 请求可能已被服务处理，但客户端未收到确定结果 | 无幂等保证时最多一次 | 是 |
| `skipped` | 本地确定无需调用，例如明确的中文翻译段 | 否 | 否 |

`uncertain` 不能降级成普通 `failed`，也不能被普通补做逻辑隐式覆盖。

### 持久化结构

在现有 `requests/` 账本基础上增加逻辑单元维度，保留旧收据兼容读取：

```json
{
  "schema": 2,
  "logical_id": "<stable digest>",
  "task_id": "...",
  "stage": "proofreading",
  "segment_start": 123.4,
  "segment_end": 130.2,
  "final_state": "uncertain",
  "attempts": [
    {
      "attempt": 1,
      "state": "uncertain",
      "request_id": "<logical_id>.1",
      "http_status": null,
      "error_category": "incomplete_response",
      "started_at": 0,
      "finished_at": 0
    }
  ]
}
```

正文、提示词、API Key、服务 URL、模型名和服务响应原文不能写入诊断日志；
请求账本是否保存成功响应仍遵守现有安全边界。

## 自动重试策略

自动重试由独立策略函数决定，不能由 UI 或阶段代码自行判断：

1. 请求确定未发出：允许有界自动重试。
2. HTTP 429 和 5xx：按现有次数、退避和取消控制重试。
3. 响应超时、响应体不完整、连接中断：标记 `uncertain`。
4. 如果服务明确支持幂等键，发送稳定 `Idempotency-Key` 后允许自动重试。
5. 没有幂等保证时，`uncertain` 最多自动重试一次；第二次仍为 `uncertain`，转为人工授权。
6. 自动重试必须增加新的 attempt 记录，不能覆盖第一次尝试。
7. 自动重试次数必须有明确上限，禁止通过外层循环和账本重试叠加成无限重试。

当前分支已有一次 `uncertain` 自动重试的过渡实现；下一轮应将它收敛到上述策略模块，
并补充真正的请求超时配置，避免单个请求长时间占用整个阶段。

## 人工补做规则

用户选择阶段就是对该阶段未知请求的明确授权，但必须在执行前显示数量和风险。

### 仅补充校对

1. 查找该任务所有 `proofreading` 阶段的 `failed` 和 `uncertain` 逻辑单元。
2. 显示：明确失败数量、结果未知数量、预计重新发送数量。
3. 用户确认后，创建新的补做任务。
4. 新任务只授权 `proofreading` 阶段的这些单元。
5. 不授权 `translation` 或 `summary`。
6. 如果校对完成后配置要求翻译，翻译作为新的依赖阶段运行；它只能使用自己的授权范围。

### 仅补充翻译

规则与校对相同，但只选择 `translation` 单元，必须真正重新调用翻译服务。
校对未知请求不会因为翻译补做而被授权。

### 摘要

摘要是独立逻辑单元。选择校对或翻译不能隐式授权摘要；摘要已有未知尝试时，
必须单独显示和授权。

一次授权必须消费一次。补做任务创建失败时不得消耗授权；任务成功建立后，
原任务保持不变，授权只复制到新任务。

## 阶段依赖与并发

依赖关系固定为：

```text
transcript -> proofreading -> translation -> summary -> exports
```

同一阶段内，不应因为一个逻辑单元 `uncertain` 而阻止其他独立单元继续执行。
只有以下情况才停止派发：

- 用户暂停、取消或退出
- 依赖阶段没有可读输入
- 当前逻辑单元正在发送同一稳定请求
- 阶段策略明确要求等待所有未知结果

默认采用严格依赖：校对阶段存在 `uncertain` 时不自动启动摘要；任务保存为
`NeedsAuthorization`，保留已完成正文和所有账本。

## 任务状态与进度

任务状态增加明确语义：

- `Succeeded`：所有必需阶段完成
- `Partial`：存在明确失败，但不存在未知请求
- `NeedsAuthorization`：至少一个阶段存在 `uncertain`
- `Failed`：没有产生可用正文或基础输入
- `Cancelled`：用户主动取消

每个阶段都保存四类计数：`completed`、`failed`、`uncertain`、`skipped`。
进度分母只统计该阶段的逻辑单元总数，不能把 batch 数和段数混用。

## 桌面端交互

任务卡片按阶段显示：

```text
校对：469 / 490，21 个结果待确认
[仅补充校对]

翻译：471 / 489，18 个结果待确认
[仅补充翻译]
```

按钮点击后先打开确认状态，明确说明未知结果可能已经被服务处理，重新发送可能产生
重复费用。确认后才创建补做任务。

旧的“查看待确认请求 / 全量重发”入口可以保留，作为高级恢复路径；它必须显示具体阶段、
数量和请求范围，不能把所有阶段合并成一个授权按钮。

## 实现拆分

按以下顺序实施，每一步都保持可测试：

1. 新建 AI 状态与策略模块，集中定义逻辑单元、尝试状态和重试决策。
2. 改造 `src/dispatch.rs`，让账本记录逻辑单元和 attempt 历史，兼容 schema 1 收据。
3. 改造 `src/llm.rs`，所有校对、翻译、摘要调用统一经过策略模块。
4. 改造 `src/pipeline.rs`，按阶段汇总四类计数和严格依赖状态。
5. 改造 `desktop/src/workspace.rs`，按组件生成补做任务，并将组件选择转换为授权范围。
6. 改造 `desktop/src/task_ui.rs`，展示分阶段 NeedsAuthorization 和确认对话框。
7. 保留现有诊断 JSONL，增加逻辑单元 ID、attempt 编号、授权范围和阶段结果事件。
8. 完成迁移测试后，再生成 Windows Release 包进行原生验证。

不要先修改 UI 文案或绕过账本；先完成状态模型和账本契约。

## 必须覆盖的测试

### 核心状态

- 成功响应写入 `completed`，重启不重复发送。
- 明确 400、无效 JSON、段落校验失败写入 `failed`，阶段可补做。
- 响应中断写入 `uncertain`，首次自动重试一次，第二次不再自动重试。
- 新任务明确授权后只重发选定阶段的未知单元。
- 校对授权不会改变翻译和摘要授权。
- 授权只消费一次，任务创建失败不消费。

### 阶段恢复

- 一个校对单元未知时，其他校对单元仍可完成。
- 校对有未知结果时，摘要默认不发送并进入 `NeedsAuthorization`。
- 仅补翻译会真正调用翻译服务，不会把校对未知请求当作翻译失败。
- 中文本地跳过计入 `skipped`，不计入 AI 请求数。
- 补做复用已完成逻辑单元，不重复调用。

### 数据与安全

- schema 1 收据可读取并转换成逻辑单元状态。
- 诊断日志不包含正文、密钥、URL、模型名和服务响应原文。
- 进程崩溃后，`sending` 尝试恢复为需要重新确认的 `uncertain`，不能静默自动重发。
- 同一逻辑单元并发执行时只允许一个发送者。

## 验收标准

对一门包含至少 400 个正文段的课程模拟以下场景：

1. 正常服务：校对、翻译、摘要全部 `Succeeded`。
2. 一个校对响应中断：其他段继续；任务显示校对 `NeedsAuthorization`。
3. 点击“仅补充校对”并确认：未知校对段真正发送，翻译授权范围不变。
4. 点击“仅补充翻译”并确认：未知翻译段真正发送，校对请求不发送。
5. 补做期间再次中断：只保留第二次未知结果，不能无限重试。
6. 重启应用：所有计数、请求尝试和授权范围保持一致。

验收必须检查实际 Windows 桌面应用和课程库任务记录，不能只检查 CLI 或 HTML 模拟。
