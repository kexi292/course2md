1. AI 校对/翻译失败后的进度保存、补做和任务面板状态不一致。
2. 核心语言为简体中文时，没有判断源语言已经是中文并跳过翻译。

- 未确认段落单独统计，保留请求账本和明确重发授权；任务面板优先显示待确认状态。
- 修正翻译请求使用校对服务标识的问题，并兼容旧账本身份。
- 任务沿用已保存的字幕/在线语言证据；明确为简体中文时跳过翻译。`zh` 等未注明字形的标签仍视为证据不足，不直接跳过。
- 请求校验原本已接受显式 `translation: null`，本次补充其与缺失字段、错误类型、改写原文的回归测试。
- 核心测试 134 项通过，任务执行测试 11 项通过，桌面测试 227 项通过；Clippy 和 Windows release 打包通过。忽略的环境相关测试不计入通过数。
- 本地模拟服务覆盖响应丢失、HTTP 拒绝、无效响应、改写原文，以及 20/21 段恢复、显式授权和补做后重启不重发。

## 已确认事实

- `src/llm.rs` 的 `PolishReport` 按字幕段数统计 `attempted/succeeded/failed`。
- 同一文件的 `Bar` 按 batch 数统计进度；每 20 段为一个 batch。任务记录因此同时出现两套进度单位。
- 补做任务会从原始 `timeline.jsonl` 重建完整正文，并重新遍历完整 batch。
- 已完成的外部请求由 `src/dispatch.rs` 的请求账本命中并复用，不会重新发送，但仍会计入本次进度。
- `Sending/Uncertain` 请求不会自动重发，必须由用户明确授权；这是防止服务已处理但客户端未收到响应时产生重复请求和重复费用。
- `src/llm.rs` 已允许模型对中文段落返回 `translation: null`，但 `request_chat_once` 当前要求翻译字段外层存在，模型若省略字段仍会失败。
- 当前翻译阶段只依据 `cfg.translation.enabled` 执行，没有把 `Source.original_language` 或已选字幕语言传入管线。
- `polish_chunk` 将请求失败统一折算为普通失败计数，任务面板随后可能只显示“仅补翻译”，没有保留“结果尚未确认”的动作语义。

## TODO 1：统一 AI 处理进度语义

涉及：`src/llm.rs`、`src/pipeline.rs`、`desktop/src/task_ui.rs`、`desktop/src/workspace.rs`

- [ ] 选定唯一的用户可见进度单位：建议按实际处理的字幕段数统计；batch 只作为内部调度单位。
- [ ] 让 `progress.current/total` 与 manifest outcome 的 `completed/total` 使用同一单位。
- [ ] 明确“已完成请求复用”是否计入进度，并在文案中区分“已复用”和“已发送”。
- [ ] 补做任务只对失败或未完成段落展示有效进度，不再让完整 batch 重新制造一个看似全新的进度条。
- [ ] 保留现有请求账本的幂等和防重复发送约束，不通过删除收据或自动重发来掩盖问题。

验收：任务中途退出后重启，进度可恢复；补做时已完成请求不重新发送；进度条和最终 outcome 的分母一致。
